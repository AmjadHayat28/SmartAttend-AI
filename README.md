# SmartClass AI Attendance Management System

Face-recognition attendance from classroom group photos, with strict role-based and
department-isolated access for **Super Admin**, **HOD**, **Teacher** and **Student**.

| Role | Responsible for | No access to |
|---|---|---|
| **Super Admin** (system administrator) | Departments → HOD accounts → teacher accounts; staff placement, staff status (activate/suspend) and password resets; system overview | Teacher assignments, students, approvals, face review, academics (batches/semesters/sections/courses), enrollments, attendance sessions, recognition, classroom photos, attendance reports/export |
| **HOD** (own department only; others → 404) | Teachers, students, student approvals, face review, batches, semesters, sections, courses, teacher assignments (teacher → course + section) | Other departments; course enrollments (the class's teacher manages them); **attendance sessions** (list, details, photos, recognition, corrections, deletion → 403); **attendance reports and Excel export** (403) |
| **Teacher** (the only role with attendance-session access) | Assigned classes: enroll/remove students (My Class Enrollments), take attendance, face recognition, finalize, edit student attendance and delete own attendance within `ATTENDANCE_TEACHER_CORRECTION_HOURS` (afterwards the attendance is locked), own history, **attendance reports + Excel export** for own active classes | Other teachers' attendance (404) |
| **Student** | Own profile, face enrollment, own subjects and attendance % | Editing or deleting attendance; anyone else's data |

These are explicit domain permissions enforced by the API (`require_roles` per router), not
"super admin = allowed everywhere". The super admin keeps read-only course/structure lookups
only because the Teacher Assignments form needs them.

| Layer | Stack |
|---|---|
| Frontend | React 19 · TypeScript · Tailwind CSS 4 · React Router 7 · Axios (Vite) |
| Backend | Python 3.11 · FastAPI · SQLAlchemy 2 · Pydantic Settings |
| Database | PostgreSQL |
| Auth | JWT (access + refresh) · bcrypt |
| Python tooling | **uv** (`pyproject.toml` + `uv.lock` + `.venv`) |
| Later phases | OpenCV · InsightFace (ArcFace embeddings, cosine similarity) · pandas + openpyxl |

## 6. Phase 3 — academic and account management

All management endpoints are under `/api/v1`. Super admins work university-wide. HODs are
always scoped to their own department on the server: a `department_id` they send is never
trusted, and other departments' records answer **404**.

| Area | Endpoints | Who |
|---|---|---|
| HODs | `GET/POST /hods`, `GET/PATCH /hods/{id}` | Super admin |
| Teachers | `GET/POST /teachers`, `GET/PATCH /teachers/{id}` | Admin, HOD (own dept) |
| Students | `GET/POST /students`, `GET/PATCH /students/{id}` | HOD (own dept) |
| Account status | `PATCH /accounts/{user_id}/status` (approve, reject, suspend, reactivate) | Super admin for HODs and teachers; HOD for own teachers and students |
| Password reset | `POST /accounts/{user_id}/reset-password` | Super admin for HODs and teachers; HOD for own teachers and students |
| Batches, semesters, sections, courses | `GET/POST /batches`, `GET/PATCH /batches/{id}`; the same shape for `/semesters`, `/sections`, `/courses` | HOD |
| Structure tree | `GET /academics/structure` (department → batch → semester → section) | Super admin (read, for department pickers), HOD |
| Teacher assignments | `GET/POST /assignments`, `DELETE /assignments/{id}` | HOD (own dept); super admin, teachers and students get 403 |
| Enrollments | `GET /enrollments/classes`, `GET /enrollments?assignment_id=`, `GET /enrollments/candidates?assignment_id=`, `POST /enrollments`, `DELETE /enrollments/{id}`, `POST /enrollments/bulk` | The class's teacher (own active assignment) |

List endpoints accept `page`, `page_size` (≤ 200), `q` (search) and resource-specific filters
(`department_id`, `status`, `is_active`, `batch_id`, `semester_id`, `section_id`, …).

**Rules enforced on the server**
- **HODs:** one *current* HOD per department. Appointing another fails with 409 unless
  `replace_existing: true` is sent; the outgoing HOD then loses the post, is suspended, and
  their sessions are revoked. A former HOD can't be reactivated until they're re-assigned to a department.
- **Uniqueness:** emails are unique and case-insensitive. Employee IDs are unique across all
  staff (HODs and teachers). Registration numbers are unique. Course codes are unique within a
  department; batch names are unique within a department (case-insensitive). Semester numbers
  are unique within a batch; section names are unique within a semester.
- **Normalisation:** registration numbers, employee IDs, section names and course codes are
  trimmed and upper-cased; names have repeated spaces collapsed.
- **Semester names** default to `Semester N`. A batch has at most one current semester.
- **Teacher assignments:** the teacher, course and section must all be in the same department.
  The teacher must be active, and the course and section active. Duplicates return 409.
  Removing an assignment deactivates it; re-creating it reactivates the same row.
- **Enrollments** are managed by the teacher of the class, through one of their own active
  assignments (`assignment_id`). The student must be placed in that assignment's section,
  semester and department; the course and section must be active, and the student's account
  active or pending. Another teacher's class, a removed assignment or another department's
  student returns 404. HODs assign classes but don't enroll students; HODs and the super admin
  get 403.
- **Bulk enrollment** enrolls every eligible student of the class's section into its course and
  returns newly enrolled, already enrolled and skipped counts, plus validation details.
  `dry_run: true` previews without writing anything.
- **Moving between departments:** a teacher or student must first have their active
  assignments or enrollments removed.
- **Changing a student's section** within the same semester moves their enrollments too.
  Moving them to a new semester closes the previous semester's enrollments.
- **Nothing is hard-deleted.** Records are deactivated, because attendance history references them.
- **Audit log:** every create, update, status change, assignment, enrollment, bulk run and
  password reset is recorded with old and new values, IP and user-agent. Passwords are never logged.

## 7. Phase 4 — profile photos and face enrollment

Students upload **one profile photo** and **3–5 face photos**: front, slight left and slight
right are required, plus up to 2 optional extras. Phase 6 will turn these into embeddings;
Phase 4 does **no recognition and no embeddings**.

**Flow:** register → (onboarding token) → profile photo → face photos → submit → department
review. Account approval and face-enrollment approval are **separate**: an account can be
active while face enrollment is incomplete. Attendance recognition (Phase 6) will require both
(`face_enrollment_service.recognition_eligible`).

| Face status | Meaning |
|---|---|
| `not_started` | No face photos yet |
| `incomplete` | Draft; photos being added (it can be submitted once front, left and right exist) |
| `pending_review` | Submitted; shown to reviewers as "Ready for review". Changing any photo withdraws it |
| `approved` | Locked; only a reviewer's "request retake" unlocks it |
| `rejected` | Retake required; the reviewer's reason is shown to the student |

**Validation:** every check runs on the server; the browser only pre-checks for speed.
1. Size ≤ `MAX_UPLOAD_SIZE_MB`. Oversized multipart requests are refused from their
   `Content-Length` before parsing, and every upload is length-checked again while it's read.
2. The declared type must be `image/jpeg` or `image/png`, *and* Pillow must find that exact
   format in the bytes. Extensions and filenames are ignored.
3. Full decode (corrupt or truncated files are rejected), a decompression-bomb pixel limit,
   EXIF orientation applied, and the shorter side must be ≥ `IMAGE_MIN_DIMENSION` (warning
   below `IMAGE_RECOMMENDED_MIN_DIMENSION`).
4. Blank-image check.
5. **Exactly one face**, using OpenCV's built-in YuNet detector (`cv2.FaceDetectorYN`;
   bundled model, SHA-256 pinned): 0 faces or more than 1 face is rejected.
6. Quality is measured on the face itself: severe blur or extreme dark/overexposure fails;
   mild issues and a small face are stored with a **warning**. Every threshold is configurable
   (`FACE_*` in `.env.example`).
7. Accepted images are **re-encoded** to a fresh JPEG (≤ `IMAGE_STORE_MAX_DIMENSION`), which
   strips EXIF/GPS metadata and any embedded payload. Failed uploads are never stored.

OpenCV 5 no longer ships Haar cascades, so detection uses YuNet. Its ~230 KB model (MIT,
`opencv/opencv_zoo`) lives in `backend/app/face_recognition/models/`. No new Python
packages were added.

**Storage and access**
- Files are saved as `uploads/faces/<student_id>/<uuid>.jpg` and
  `uploads/profiles/<student_id>/<uuid>.jpg`.
- Only that exact path shape can ever be resolved (a whitelist), which rules out path traversal.
- Files are written atomically; a replaced file is deleted only after the database commit succeeds.
- `uploads/` is never served statically. Images come only from authorised endpoints with
  `Cache-Control: private, no-store`, and the API never returns filesystem paths.
- Face photos can be viewed by the student and the student's HOD (not the super admin).
- Profile photos can also be viewed by teachers who teach the student.

**Pending students** can't sign in, so registration returns a 60-minute **onboarding token**
that works *only* on `/me/face-*` and `/me/profile-photo` (plus viewing their own images).
To resume later, they use `POST /auth/onboarding-token` with their email and password
(rate-limited like login).

| Area | Endpoints |
|---|---|
| Student (own) | `GET /me/face-enrollment`, `PUT /me/profile-photo`, `POST /me/face-photos` (form: `pose`, `file`), `PUT/DELETE /me/face-photos/{id}`, `POST /me/face-enrollment/submit` |
| Images | `GET /face-photos/{id}/image`, `GET /students/{id}/profile-photo` |
| Review (HOD) | `GET /face-enrollments`, `GET /face-enrollments/{student_id}`, `POST …/approve`, `POST …/reject` (`reason` required) |
| Onboarding | `POST /auth/register/student` → `onboarding_token`; `POST /auth/onboarding-token` |

**Audit:** profile-photo upload/replace, face-photo upload/replace/delete, and enrollment
submit/withdraw/approve/reject are all logged with metadata only (pose, size, status, reason).
Logs never contain image bytes, base64 or file paths. Tests use **synthetic drawn faces only**
(`tests/imaging.py`).

## 8. Phase 5 — taking attendance (manual marking, review, finalization)

Teachers take attendance for their **own active assignments** only (enforced by the API).
**Flow:** Take Attendance → pick class, date and session number → **Start** (creates a draft,
or resumes your own draft for that slot) → mark P / A / L / E, add notes and classroom photos →
**Review & finalize**.

| Rule | Behaviour |
|---|---|
| States | `draft` → `finalized` (official) or `cancelled` (kept for audit; frees the slot) |
| Duplicates | One non-cancelled session per course + section + date + session number. A finalized slot returns 409 "Attendance for this class, subject, date and session already exists." |
| Roster | A snapshot of active enrollments taken when the draft starts. Resuming a draft adds newly enrolled students; a finalized roster never changes |
| Default status | **Not marked.** Finalizing is blocked until everyone is marked ("Rest absent" does that in one click). This is safer than defaulting to Absent, which can finalize students who were never looked at |
| Dates | No future dates; at most `ATTENDANCE_MAX_BACKDATE_DAYS` back; session number ≤ `ATTENDANCE_MAX_SESSIONS_PER_DAY` |
| Auto-save | Every change saves after ~0.6 s through a serial queue, with a "Saving… / All changes saved" indicator and a warning before leaving with unsaved changes |
| Concurrency | Each change sends the session `version`. A stale version (another tab or device) gets **409**, and the editor locks and offers "Reload the latest version" |
| Photos | Up to `ATTENDANCE_MAX_PHOTOS` per session (default 5), from the camera (rear) or file upload. Same storage and validation as Phase 4 except the face rule: group photos are expected. Stored under `uploads/attendance/<session_id>/`, served only to the session's teacher. Read-only after finalizing |
| Corrections | Finalized records change only via `POST /attendance/records/{id}/correct` with a **reason**, by the session's teacher only, within `ATTENDANCE_TEACHER_CORRECTION_HOURS` (default 24). After that the attendance is **locked** — no HOD or super-admin override (an exceptional unlock workflow would be a separate, explicit feature). The `hod_override` method value remains only for historical records. Each correction is stored in `attendance_modifications` (old/new value, reason, who, when) and the audit log. UI: **Edit Student Attendance** |
| Delete Attendance | For a session that is wrong or unnecessary as a whole: `POST /attendance/sessions/{id}/delete` with `{"reason": "…"}` (≥ 5 chars; optional `version` → 409 if stale) → **204**. A real delete of **only that session**: its records, corrections (`attendance_modifications`), recognition runs and faces, photo metadata and photo files. One transaction (any failure rolls everything back); files are removed only after the commit. Other sessions/dates/courses/sections, students, enrollments and assignments are untouched, and the same course + section + date + session-number slot is simply free again (no special retake logic). Only finalized sessions — a draft is discarded with `…/cancel`. Only the teacher who created/finalized the session, still assigned, within `ATTENDANCE_TEACHER_CORRECTION_HOURS`; HOD and super admin: 403. UI: **Delete Attendance** → confirm with a reason → back to Attendance History |

**Attendance % policy** (`services/attendance_policy.py`, configurable). Only **finalized**
sessions count:
`attended = present + late × ATTENDANCE_LATE_WEIGHT (+ excused if policy = present)`,
`conducted = all records (− excused if policy = exclude)`. The default policy is
late = 1.0 and excused = *exclude*. It's used by the student subject cards, the teacher's
class cards, session summaries, today's % on the dashboards, Student My Attendance and the
teacher reports/Excel export. One threshold, `LOW_ATTENDANCE_THRESHOLD` (default 75), drives
every low-attendance warning (student pages, student dashboard, teacher reports).

| Who | Endpoints |
|---|---|
| Teacher | `GET /attendance/classes`, `POST /attendance/sessions` (create/resume), `PATCH /attendance/sessions/{id}/records`, `POST …/bulk` (`all_present`, `all_absent`, `unmarked_absent`, `reset`), `PATCH /attendance/sessions/{id}` (note), `POST/DELETE …/images`, `POST …/finalize`, `POST …/cancel` |
| Teacher (own sessions only) — HODs and the super admin get 403 | `GET /attendance/sessions` (filters: status, date range, course, semester, section, `q`), `GET /attendance/sessions/{id}`, `GET /attendance/images/{id}`, `POST /attendance/records/{id}/correct`, `POST /attendance/sessions/{id}/delete` |

**Audit:** session created, roster synced, records updated (old/new per student), bulk action,
note changed, photo uploaded/removed, finalized (with counts), cancelled, record corrected, session deleted
(`attendance.session_deleted`: metadata only — session id, course id/code/title, section id/name,
date, session number, teacher id, reason, deleting user and role, timestamp; no student records).
No image data or file paths are logged.

## 9. Phase 6 — face recognition (assists the teacher; never decides alone)

**Workflow:** draft session → classroom photo(s) → **Run Face Recognition** → review →
finalize manually. Recognition compares faces **only with the session roster**, and only with
students whose account is active *and* whose face enrollment is approved.

| Result | What happens |
|---|---|
| Confident (≥ `FACE_MATCH_CONFIDENT`, clear margin) | Pre-fills **Present** (method `face_recognition`, with confidence), but only if the student is **not marked yet** |
| Low confidence (between the two thresholds) | Suggestion only; the teacher accepts, picks another student, or marks it unknown |
| Ambiguous (top two within `FACE_MATCH_AMBIGUITY_MARGIN`) | The teacher chooses |
| Duplicate (same student, weaker face, same photo) | Flagged for review; one-to-one assignment per photo |
| No match | Shown as an unknown face; the teacher may link it to a **roster** student |

**Safety rules**
- Never finalizes, and never marks anyone Absent.
- Teacher decisions are preserved: manual marks, bulk actions and confirmed suggestions are
  never overwritten. A conflicting confident match is recorded as `manual_kept`.
- **Re-runs** clear only *unconfirmed* AI marks before recomputing; unmatched students go back
  to "not marked", never to Absent.
- **The same student in several photos** is counted once (the strongest sighting is primary).

**Model**
- InsightFace `buffalo_l` (classroom model): SCRFD-10GF detector + ArcFace ResNet-50, 512-d
  embeddings, CPU via ONNX Runtime. Smaller packs: `buffalo_s`, `buffalo_sc`.
- **Fallback:** if `FACE_RECOGNITION_MODEL` cannot be loaded, `FACE_RECOGNITION_FALLBACK_MODEL`
  (default `buffalo_sc`) is used. Never silently: the log says so, the run gets a teacher-visible
  warning, and the run's `diagnostics.fallback_from` records it. The model is loaded once per
  process and reused.
- Packs come from the official InsightFace GitHub release `model-zoo` and are verified against
  the SHA-256 GitHub publishes for each asset (pinned in `face_recognition/model_store.py`).
- Per-file checksums are re-checked on every load.
- Stored in git-ignored `models_cache/insightface/`.
- Downloads never happen inside a request by default (`FACE_RECOGNITION_ALLOW_DOWNLOAD=false`).
- The downloader resumes with HTTP Range, accepts a resume only when the server's
  `Content-Range` starts where the partial file ends, allows one writer at a time (`.part.lock`),
  and sets aside (renames, never deletes) a partial that is longer than the real file.
- **Licence:** InsightFace pretrained packs fall under InsightFace's *non-commercial* terms
  unless a commercial licence is obtained. Review before production use.

```powershell
uv run python -m backend.app.scripts.download_face_models             # default pack (buffalo_l, ~289 MB, resumable)
uv run python -m backend.app.scripts.download_face_models buffalo_sc  # small pack (~15 MB)
uv run python -m backend.app.scripts.generate_face_embeddings         # backfill / refresh embeddings
uv run python -m backend.app.scripts.calibrate_recognition --session 42           # dev only
uv run python -m backend.app.scripts.calibrate_recognition --probes D:\probes   # dev only
uv run python -m backend.app.scripts.benchmark_recognition D:\dataset --packs buffalo_l buffalo_sc  # dev only
```

**Group-photo detection** (`face_recognition/classroom.py`). Face *detection* confidence
(`FACE_RECOGNITION_MIN_DET_SCORE`) is separate from *identity* similarity (`FACE_MATCH_*`).
1. **Orientation** (`FACE_RECOGNITION_AUTO_ORIENT`): photos forwarded through messaging apps can
   arrive sideways with no EXIF. A 640 px pass at 0°/90°/270° rotates only when a sideways
   orientation is clearly better; skipped when upright faces already score ≥ 0.80.
2. **Full image** at 640 and `FACE_RECOGNITION_DET_SIZE` (multi-scale).
3. **Tiles** (`FACE_RECOGNITION_TILING`, `…_TILE_SIZE`, `…_TILE_OVERLAP`): for photos larger than
   1.25 × the tile size, overlapping native-resolution tiles find small/distant faces the
   downscaled full pass cannot see. Tile boxes cut by an interior tile edge are dropped.
4. **Merge** (`FACE_RECOGNITION_NMS_IOU` + containment): full-image detections first; tiles only
   add faces the full pass missed (a tile detection of a large face has worse landmarks).
All boxes and landmarks are mapped back to the stored photo's pixels, so overlays line up.

**Enrollment quality:** with ≥ 3 approved photos, an embedding whose mean similarity to the
student's other photos is below `FACE_ENROLLMENT_MIN_CONSISTENCY` (0.2) is left out of matching,
so one wrong-person or unusable photo cannot attract other people's faces.

**Run diagnostics** (`run.diagnostics`, shown under the recognition summary): model and detector
actually used, fallback, per-photo rotation/tiles/merged boxes and detection / recognition /
matching / total time. No vectors, pixels or file paths.

**Embeddings:** one per approved enrollment photo (front, left, right, extras), L2-normalised,
stored as float32 bytes in `face_embeddings`; a face's score is the best over that student's
embeddings.
- **Generated:** in the background after approval, lazily before a recognition run if missing
  or stale, or by the backfill script.
- **Deleted at once** when a reviewer requests a retake.
- **Stale and never used** after a model change or a photo change.
- **Never** exposed by any API, written to logs or put in audit entries.

**Thresholds** (`FACE_MATCH_*`: confident 0.50, low 0.35, margin 0.06) were checked in Phase 8
with `benchmark_recognition` on a small labelled set (3 consenting students, 4 real group/selfie
photos, InsightFace's 6-stranger sample photo, 4 masked faces, and small-face composites at
20–96 px). Highest impostor score: 0.20 (`buffalo_l`) / 0.24 (`buffalo_sc`); lowest genuine score
0.43 / 0.34. No false or wrong-student match at any tested threshold, so the thresholds were left
unchanged — the sample is far too small to justify lowering them. Re-run the benchmark on your own
consented, labelled classroom photos before changing them.

**YuNet vs InsightFace:** Phase 4's YuNet keeps validating enrollment uploads (exactly one face,
quality). InsightFace does detection and embeddings for recognition. They are kept separate on
purpose so the working Phase 4 validation is unchanged.

| Endpoint | Who |
|---|---|
| `POST /attendance/sessions/{id}/recognition` (`version`) | The session's teacher (draft only) |
| `GET /attendance/sessions/{id}/recognition` | Teacher (own) |
| `POST /attendance/recognition/faces/{face_id}/accept \| assign \| reject` | The session's teacher (latest run, draft only) |

### Phase 9 — recognition job safety and limits

- **Progress is real, not estimated.** A run records the step it is on (`detecting` photo *k* of
  *n* → `matching` → `saving`) and the editor polls it; no percentages are invented. Steps before
  the run exists (saving pending edits, roster, student profiles) show as "Preparing recognition".
- **One run at a time** per session, enforced by a partial unique index (migration `0007`).
  While a run is going, photo upload/removal, finalize and discard are refused (409) and disabled
  in the editor. A run never applies to a session that was finalized or discarded meanwhile.
- **Time limit:** `FACE_RECOGNITION_TIMEOUT_SECONDS` (240) is checked between photos; a stopped run
  changes nothing. A run left `processing` by a server restart shows as *interrupted* after the
  limit + 60 s and can simply be run again.
- **Errors:** the teacher gets a plain message (model unavailable, photo #*n* unreadable, took too
  long, already running, unexpected failure); technical details go to the `smartclass.*` log only.
  Any unhandled error returns a generic JSON 500 without stack traces.
- **Model:** loaded once per process, in a background thread at startup
  (`FACE_RECOGNITION_PRELOAD`); after a failed load, requests are refused at once for
  `FACE_RECOGNITION_RETRY_SECONDS` instead of re-hashing ~300 MB of model files per request.
- **Classroom photo limits:** JPEG/PNG only (content must match the declared type), ≤
  `MAX_UPLOAD_SIZE_MB` (checked by Content-Length *and* while streaming, so chunked uploads are
  cut off too), ≤ `IMAGE_MAX_PIXELS` (checked from the header before decoding), short side ≥
  `ATTENDANCE_PHOTO_MIN_DIMENSION`, long/short ≤ `ATTENDANCE_PHOTO_MAX_ASPECT_RATIO`. Photos up to
  2560 px are stored unchanged in size; larger ones are scaled to 2560 px (the size the Phase 8
  small-face benchmark was run at).
- **Speed:** the upright orientation check and the full-image pass share their identical 640 px
  detector pass (same results, one detector pass less per photo).

## 10. Phase 7 — Student My Attendance, teacher reports and Excel export

Only **finalized** sessions count everywhere below (drafts, cancelled and deleted sessions never
do). Every percentage and low-attendance flag comes from the backend policy above; the frontend
never calculates them.

**Student — My Attendance** (`/student/history`). The student is always the signed-in account;

|---|---|
| `GET /reports/classes` | The teacher's active classes |

## 12. Security model

- **Passwords**: bcrypt (cost 12). Plain-text passwords are never stored or logged.
- **Tokens**: short-lived access JWT (30 min, kept in memory by the page, sent as a Bearer header)
  and refresh JWT (7 days) that exists only as an **HttpOnly, Secure (production), SameSite=Strict
  cookie** scoped to `/api/v1/auth` — page JavaScript can never read it, and it is never returned in
  JSON or stored in localStorage. Refreshing with the cookie also requires the header
  `X-Requested-With: SmartClass` (a cross-site page cannot send it), on top of SameSite=Strict.
  `POST /auth/logout` deletes the cookie. Each refresh issues a renewed cookie; earlier refresh tokens
  stay valid until they expire (no reuse detection) — change the password to end every session. Each token carries
  `token_version`. Changing a password, suspending, or rejecting an account bumps that version,
  which revokes every outstanding token immediately.
- **Every request** reloads the user and checks `status == active`.
- **RBAC**: `require_roles(...)` dependencies (`AdminUser`, `AdminOrHod`, `HodUser`, `TeacherUser` — every attendance-session endpoint, `StudentUser`).
- **Department isolation**: `services/scoping.py` resolves the caller's department and filters queries, and
  `ensure_department_access()` returns **404** for other departments' resources so their
  existence isn't revealed. `ensure_teacher_assignment()` limits teachers to course+section
  pairs they're assigned to.
- **Login rate limit**: 5 failures per IP+email per 5 minutes returns 429 with a `Retry-After`
  header. In production the counts live in PostgreSQL (`login_attempts`, SHA-256 keys only), so all
  workers share them and a restart does not reset them; a per-key advisory lock stops parallel
  attempts slipping past the limit. Development uses an in-process counter (one worker only).
- **No user enumeration**: unknown emails and wrong passwords get the same response and the same timing.
- **Audit log**: logins, registrations, approvals and rejections, and department changes, with IP and user-agent.
- **Session row locks**: every change to an attendance session (edits, photos, recognition start
  and apply, finalize, discard, corrections, delete) takes `SELECT … FOR UPDATE` on the session
  row, so its version and status checks always see the latest committed state. Two concurrent edits
  can never both succeed; the second gets 409 "changed in another tab".
- **Server log** (`smartclass.*` loggers): model load and fallback, failed and rate-limited logins,
  one line per audited action (who, what, which record; never the old/new values), recognition
  failures, and unexpected errors with stack traces. Never logged: passwords, tokens, embeddings,
  image bytes or request bodies. Users only see plain messages (no stack traces, no SQL).
- **Safe failures**: database unavailable → 503 "temporarily unavailable"; any unhandled error →
  generic 500; duplicates → 409; stale edits → 409 with a reload prompt.
- **Production configuration**: with `ENVIRONMENT=production` the server refuses to start with a
  placeholder or short `JWT_SECRET_KEY`, `DEBUG=true`, a SQLite or default `DATABASE_URL`,
  `CORS_ORIGINS` that are not all `https://` (or are the development defaults), an empty
  `APP_TIMEZONE`, or `AUTH_COOKIE_SECURE=false`. The error names the settings but never prints their
  values. `CORS_ORIGINS` never accepts `*` (credentials are allowed). `/docs` is off in production.
- **Health**: `GET /health/live` (process up) and `GET /health/ready` (database and upload storage
  usable → 200, else 503; face-recognition state reported as `ready`/`loading`/`fallback`/
  `unavailable` without failing readiness). Only coarse states — no hosts, paths or errors.

### Biometric privacy

- **Embeddings** (512 numbers per enrollment photo) live only in `face_embeddings.embedding_vector`.
  No API returns them (not even to the super admin). They are never logged, never written to audit
  entries, never exported to Excel, and they are deleted as soon as a retake is requested.
  Automated tests check API responses, the OpenAPI schema, the audit log and the Excel export.
- **Recognition results** (face boxes, suggestions, scores) are visible only to the teacher who owns
  the attendance session. HODs, the super admin and students get 403; other teachers get 404.
- **Classroom photos**, and the face crops the teacher sees (drawn in the browser from the photo),
  are served only to that teacher, with `Cache-Control: private, no-store`.
- **Enrollment photos** are visible to the student, and to their own department's HOD for review.
- **Files** live outside the web root under random names. Stored paths are whitelisted, so no
  request can read or overwrite another file. Back them up and restrict access like the database
  (section 14).

**4. Backend and reverse proxy on Windows (tested in Phase 11).** Everything below runs without
administrator rights; `deploy/windows/` holds the scripts and the Caddy configuration.

| Piece | Where | Bound to |
|---|---|---|
| PostgreSQL 17 (own cluster, SCRAM, loopback only) | `D:\SmartClassDeploy\pgdata` | 127.0.0.1:5432 |
| Backend: uvicorn, `ENVIRONMENT=production`, 1 worker | the project checkout | 127.0.0.1:8001 |
| Caddy 2 reverse proxy (HTTPS, frontend, `/api`) | `D:\SmartClassDeploy\bin\caddy.exe` | https://localhost (staging) |
| Settings + secrets (ACL: this user only, never in Git) | `D:\SmartClassDeploy\config` | — |
| Frontend build, uploads, logs, backups | `D:\SmartClassDeploy\{www,uploads,logs,backups}` | — |

```powershell
# One-time: register the three processes as Task Scheduler tasks (start at logon of this user)
powershell -ExecutionPolicy Bypass -File deploy\windows\setup_tasks.ps1      # -Workers 1 (default)
powershell -ExecutionPolicy Bypass -File deploy\windows\control.ps1 start    # also: stop, status
```

- Each task runs `deploy/windows/supervise.py` under `pythonw.exe`: it restarts its process on any
  exit (backoff 1 s → 30 s), writes rotated logs (10 MB × 5) to `logs\`, stops cleanly via a stop file
  (`control.ps1 stop`; PostgreSQL with `pg_ctl stop -m fast`), and keeps the whole process tree in a
  Job Object so nothing is orphaned. Task Scheduler restarts a failed supervisor every minute.
- The backend reads `D:\SmartClassDeploy\config\production.env` via `SMARTCLASS_ENV_FILE`; the
  project's own `.env` is not used by the production process.
- Measured (Phase 11): restart → ready ≈ 10–19 s, face model loaded ≈ 20 s; backend crash → proxy
  answers 503 "restarting" at once, API back in ≈ 12–19 s; Caddy crash → HTTPS back in ≈ 6–10 s;
  PostgreSQL stopped → API 503 in ≈ 2 s, recovers ≈ 1 s after it is back (no backend restart);
  logoff/logon → everything restarted by the logon tasks, PostgreSQL crash recovery in 0.06 s.
- **Workers: use 1 on Windows.** Measured: 1 worker ≈ 1.3 GB private memory; 2 workers ≈ 2.1 GB
  with no throughput gain (two simultaneous recognitions take 14 s + 28 s either way: one run
  already uses ~4 CPU threads, and uvicorn workers do not share load evenly on Windows). With one
  worker, other requests stay fast during a recognition (median 67 ms).
- **Limitation without admin rights:** the tasks run only while this user is logged on. With admin
  rights, register the same supervisor command lines as services (NSSM/WinSW) or set the tasks to
  "run whether user is logged on or not", so the system also starts at boot.
- **Linux:** a systemd unit per process (same commands, `Restart=always`, a dedicated user owning
  `UPLOAD_DIR`) replaces the supervisor; the Caddyfile works unchanged.

**5. Reverse proxy (`deploy/windows/Caddyfile`).** Serves the published build from `www`, sends
`/api/*` to the backend (with `X-Forwarded-*`; uvicorn trusts them from 127.0.0.1 only), falls back to
`index.html` for deep links, never lists directories, caches hashed `/assets/*` for a year and
revalidates everything else, and adds HSTS, `nosniff`, `X-Frame-Options: DENY`, Referrer-Policy,
Permissions-Policy and a Content-Security-Policy (same-origin only; inline style attributes allowed
for React). Upload bodies above 8256 KiB (the backend's 8 MiB + 64 KiB framing) are refused by the
proxy with a JSON 413 — keep this in step with `MAX_UPLOAD_SIZE_MB`. When the backend is down the
proxy answers a JSON 503 "service is restarting". `/health/ready` is not published.

- **HTTPS (staging):** `tls internal` — Caddy's own local CA issues the `localhost` certificate. The
  CA is not installed into Windows automatically (`skip_install_trust`); trust
  `D:\SmartClassDeploy\caddy-data\pki\authorities\local\root.crt` deliberately (Windows "Trusted
  Root Certification Authorities" for this user, or `curl --cacert`). HTTP → HTTPS redirect (308).
  `default_bind 127.0.0.1 [::1]` keeps the staging site on this machine.
- **Real server:** set `SMARTCLASS_SITE` to the public DNS name, delete `tls internal` (Caddy then
  obtains a publicly trusted certificate) and delete `default_bind`. Set `CORS_ORIGINS` to
  `https://<that name>`.
- **nginx equivalent:** `location /api/ { proxy_pass http://127.0.0.1:8001; client_max_body_size 8256k;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_set_header X-Forwarded-Proto $scheme; }`
  and `location / { root /srv/smartclass/www; try_files $uri /index.html; }`, plus the same headers.

If the frontend must live on a different origin, build it with
`$env:VITE_API_BASE_URL="https://api.your-university.edu/api/v1"; npm run build` and list the
frontend's origin in `CORS_ORIGINS` (the refresh cookie then needs `AUTH_COOKIE_SAMESITE=lax` only
if the two are different *sites*, not merely different subdomains).

## 14. Backup and restore

Back up **both** the database and `UPLOAD_DIR` (face and classroom photos) at the same time; one
without the other is incomplete. Keep backups encrypted and access-controlled: they contain
student personal data and face embeddings. Never commit them (`*.dump`, `*.db` and `backups/` are
git-ignored).

**Scripts (tested in Phase 11):**

```powershell
# Custom-format pg_dump, timestamped, verified (non-empty, readable TOC), SHA-256 logged,
# optional photo archive, retention (default 14 days), log in logs\backup.log
powershell -ExecutionPolicy Bypass -File deploy\windows\backup_postgres.ps1 -IncludeUploads

# Restore drill: newest dump → NEW database, compare migration version + every table's row count,
# start a temporary backend on it (ready + login + history), then drop it (--keep to retain)
.venv\Scripts\python.exe deploy\windows\restore_drill.py
```

The password is read from the ACL-restricted secret file and never printed. Schedule the backup with
Task Scheduler (example in the script header).

**Manual commands** (supply the password through `PGPASSWORD` or a pgpass file, never in scripts):

```powershell
# Backup (custom format, compressed)
pg_dump -h db-host -U smartclass -d smartclass -Fc --no-owner -f smartclass-2026-10-18.dump

# Restore into a NEW, empty database, then point DATABASE_URL at it
createdb -h db-host -U postgres -O smartclass smartclass_restored
pg_restore -h db-host -U smartclass -d smartclass_restored --no-owner --exit-on-error smartclass-2026-10-18.dump
```

A backup → restore round trip was verified on test data (same migration version and row counts).
After restoring, run `uv run python -m backend.app.database.init_db` to apply any newer migrations.

**Uploads**: copy the folder, e.g. `robocopy D:\smartclass-data\uploads E:\backup\uploads /MIR` or
`rsync -a /var/lib/smartclass/uploads/ backup-host:/backups/uploads/`.

**SQLite (local development only)**: stop the server and copy `smartclass.db` together with
`uploads/`, or take a live copy with `sqlite3 smartclass.db ".backup smartclass-backup.db"`.
